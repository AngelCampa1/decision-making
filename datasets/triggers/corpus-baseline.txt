# Corpus findings that are on the record and deferred.
#
# One `<corpus path>|<finding key>` per line, `#` for comments. Same semantics
# as `paper/citations-baseline.txt` and `results/provenance-baseline.txt`:
# exempt, and it MAY ONLY SHRINK. `de check` fails when a listed entry no
# longer matches a real finding, because a baseline that does not shrink when
# work is done has stopped measuring anything.
#
# A line here is not "this is fine". It is "this defect is on the record and
# nobody is pretending otherwise" -- and unlike the other two baselines, these
# entries are *printed on every run* by `check_triggers_step`, so a green gate
# cannot be read as a clean corpus.
#
# WHAT A BASELINE HERE CANNOT DO. Only the shortcut battery's findings carry a
# key. A structural defect -- a case with no band, a triple that is not one
# positive and two negatives, a band whose members are not the length it claims
# -- carries no key and cannot be listed, because there is no backlog to defer:
# it is fixable in the time it takes to read the message.
#
# AND THE KEYS ARE NARROW ON PURPOSE. A derived view's key names the entire set
# of leaking features. A fifth feature joining the set below is a different key
# and fails the build; so is the leak appearing on the `ask` or `turn` view; so
# is any other feature going inert. Dropping to three features is also a
# different key and also fails, which is the may-only-shrink rule doing its job
# -- an improvement nobody recorded is an improvement the baseline has stopped
# being able to see.
#
# Seeded 2026-08-13 with two findings, both produced the day the battery was
# given a guard against checks that could not fail and a view of the closing
# ask. Neither threshold was moved to accommodate them.

# four-feature `close`-view leak no longer holds with that feature set. Neither
# was closed by moving a threshold. They are deleted rather than kept, which is
# the may-only-shrink rule working in the direction it was written for.

# cancel as cleanly on every feature.

# ADDED 2026-08-14, uncovered by the same long-band merge that closed
# `word_count` above (`l10`-`l22`, `xl08`-`xl17`, 261 items, 87 triples). Not
# new features and not a new gate -- these three sat under z = 3.0 on the
# pre-merge corpus and the merge pushed them over it. The mechanism is the one
# the `word_count` entry above names directly: the 23 new triples are skewed
# 16-of-23 positive-shortest against a projected uniform split, and that skew
# shows up on every length-correlated feature, not only `word_count`.
#
# `sentence_count`, turn and ask views: the *matched* statistic stays quiet --
# 0.480, 0.58 null standard errors, well inside chance -- but the *dispersion*
# statistic does not: 3.82 null standard errors, above the z = 3.0 gate on
# both views. That is the `cancel:` finding, not the `matched:` one: the
# positive sits at an extreme of its own triple (highest or lowest sentence
# count) far more often than chance while which extreme it sits at is
# balanced enough that the directional average is near 0.5. Per band,
# matched: s 0.552, m 0.625, l 0.432, xl 0.235 -- `s`/`m` above chance,
# `l`/`xl` below, the same up/down split across bands that the pooled AUC has
# already been shown to cancel elsewhere in this corpus. Pooled AUC 0.517
# (turn), 0.466 (ask).
#
# `type_token_ratio`, ask view only: this one *is* a `matched:` finding --
# 0.316 of comparisons, below chance, 4.27 null standard errors. Per band:
# s 0.375, m 0.417, l 0.205, xl 0.235 -- below chance in every band, strongest
# in `l` and `xl`, so this is not a cancellation the way `sentence_count` is;
# the four bands agree on direction. Pooled AUC 0.389. The `turn` view of the
# same feature sits at 2.93 null standard errors -- under the gate, and the
# closest a checked-and-passing feature gets to it in this corpus.
#
# WHAT IT DOES AND DOES NOT MEAN. Same reading as every entry above: an arm
# sees one turn and not its triple-mates, so this is a defect in the
# construction, not a demonstrated exploit, and per-band pooled AUC remains
# the exploitability measure printed alongside it.
#
# NOT FIXED BY RE-TUNING THE NEW TRIPLES. Pushing the 23 new positives back
# toward positive-longest to flatten `sentence_count` and lift
# `type_token_ratio` would re-open the `word_count` pair just closed above --
# the four features move together because they are all reading the same
# closing-sentence habit through different rulers. Per-item retuning against
# whichever feature is currently over the line is the mechanism that produced
# "four generations of leak" the closed `word_count` entry already named;
# doing it again here would be the fifth.
#
# CLOSED BY: the same condition named for `word_count` above, applied
# corpus-wide rather than to the 23 new triples alone -- a rank distribution
# for the positive that is roughly uniform across longest, middle and
# shortest within its triple, reached at authoring time, across all 87
# triples rather than balanced band against band. Any item whose ask changes
# needs re-adjudication, because the ask is what the label rests on.

# ADDED 2026-08-19. Not a corpus leak like every entry above -- a gap between
# the corpus and the skill it is the answer key for. The shipped router table
# grew from four rows to six that day (`council`, `hinge`) and the key was not
# grown with it, so two of the six procedures the description now offers are
# the correct answer for no positive in either corpus.
#
# WHY THAT IS A MEASUREMENT DEFECT AND NOT A TODO. `evaluate_routing` scores
# `chosen in case.routes`. A model that correctly selects `council` cannot be
# credited; the answer can only ever land in `incorrect`. An arm offered six
# procedures therefore carries two ways to be wrong that the four-procedure
# arms it would be compared against did not have, and the gap between them
# reads as a description effect when it is a menu-size artefact. This is the
# fourth instance of "an estimator that cannot return a non-zero value is not a
# measurement" in this repository and the second caught in source before any
# call was made.
#
# WHY IT IS DEFERRED RATHER THAN FIXED TODAY. Authoring positives for two new
# procedures is a change to the answer key: a new `set_version`, and a set of
# published numbers that `trigger_arms.label_versions_comparable` will refuse
# to compare across. That is a unit of work with a governance cost, not a typo,
# and doing it quietly under a run in flight is how a key change gets mistaken
# for a model result -- which has happened here once already, on 2026-08-13,
# and moved recall three to five points on every arm on disk without a single
# call being re-made.
#
# WHAT IT DOES AND DOES NOT BLOCK, corrected by adversarial review 2026-08-19
# after the first draft of this entry overstated it. It blocks *less* than it
# first appeared:
#
#   - Firing is unaffected. Which procedure gets named does not change whether
#     a turn fired, and firing is the primary quantity -- `decision-making.yaml`
#     line 31 says routing "is a *secondary* label" and N7, the design template
#     for the next run, reports routing zero times.
#   - The cross-arm comparison this entry was written to prevent is *already*
#     refused mechanically. `trigger_arms.skill_versions_comparable` raises on
#     a comparison where one side stamps `skill_version` and the other does
#     not, which is exactly the six-procedure-against-four case. The guard
#     landed in 6e2028c, before this finding was noticed.
#   - The leak is *measurable* rather than merely feared: `default_procedures`
#     and `run_triggers._PROCEDURE_SCHEMA` both read the router table live, so
#     a model can say `council`, it parses, and the name is stamped into every
#     row.
#
# So what stands is narrower: a pooled routing accuracy computed here is a
# six-way choice scored against a four-way key, and its ceiling cost is not
# small -- flipping every currently-correct row on the 15 of 65 labelled items
# carrying council/hinge conditions moves the best arm 0.792 -> 0.631. The
# honest readout is routing over the four reachable procedures with the
# `council`/`hinge` selection rate reported beside it descriptively, over a
# declared denominator of 65 items / 130 rows, and no cross-run routing
# comparison registered at all.
#
# CLOSED BY: positives authored for `council` and `hinge` in both corpora, the
# key version bumped, and the arms re-run rather than re-scored. Dropping the
# two procedures from the router table would also close it and is the other
# real option; it is not the assumed one.
datasets/triggers/decision-making.yaml|unreachable:council,hinge
